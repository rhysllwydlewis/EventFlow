# CLAUDE.md

Guidance for Claude Code sessions working in this repository, distilled from
real mistakes and real findings while auditing the `admin-*.html` pages
(rhysllwydlewis/EventFlow#1733 and follow-ups). Read this before touching
admin pages, generated files, or shared button/notification styling.

## Known recurring bug classes — check for these first

These have each caused a real, shipped bug at least once. When touching
related code, check whether the same class of bug exists nearby.

- **A changed asset needs a new `?v=` on every page that loads it.**
  Everything under `public/assets/` is served with `max-age=604800` (7 days)
  behind a CDN, so returning visitors keep the old copy until the URL changes.
  The auth redesign (rhysllwydlewis/EventFlow#1763) removed the confirm-password
  field and changed `app.js` but left `app.js?v=18.5.0`; anyone with the cached
  script got "Passwords do not match" on every sign-up, and `auth-init.js` had no
  `?v=` at all so the new social icons did nothing. When you edit a JS/CSS file,
  bump (or add) the `?v=` on each page that references it, then run
  `npm run check:asset-versions` (compares against `origin/main`; a PR warning
  runs in `.github/workflows/asset-versions.yml`). Note most of the repo
  does not follow this yet, so the check warns instead of blocking.

- **`.ef-cta` squishes icon-only buttons.** `styles.css`'s `.ef-cta` class
  forces `padding: 10px 18px !important`. Any button meant to be a small
  fixed-size icon button (e.g. 32×32/40×40, just an SVG or a single
  character like `×`) that also carries `.ef-cta` will have its icon
  squeezed into a few visible pixels — it looks blank or near-invisible,
  not "broken" in an obvious way. `admin-navbar.css` has a documented
  "ICON BUTTON VISIBILITY FIX" block with resets for buttons that already
  hit this. When you add a new small `.ef-cta` icon button anywhere, add a
  matching `padding: 0 !important` (plus `font-size`/`font-weight: inherit`
  if it renders a text glyph) reset, or drop `.ef-cta` if it isn't needed.

- **Notification type/icon/colour maps must cover the full enum.**
  `models/index.js`'s `NOTIFICATION_TYPES` is the source of truth (11
  types as of this writing). `admin-navbar.js`'s `getNotifIcon()` and
  `admin-enhanced.css`'s `.admin-notif-item-icon--{type}` rules both
  hardcode a per-type map. If a type is missing from either, it silently
  falls back to a default icon **with no background colour**, and because
  the icon glyph is a hardcoded white stroke, it renders as an invisible
  icon on a white circle — not an obvious visual bug, easy to miss in a
  screenshot pass. When adding a notification type anywhere in the
  backend, grep both files and add the type to both maps in the same
  change.

- **The `/api` pagination middleware hard-caps `limit` at 100.**
  `middleware/pagination.js`, applied globally via
  `app.use('/api', validatePagination)` in `server.js`, rejects any
  request with `limit` over 100 with a 400. A frontend page requesting
  `limit=200` (or higher) will fail server-side validation on every load.
  Check any new/changed admin page's list-loading code for a `limit` over
  100 before shipping it.

- **Similarly-named features are not always duplicates — verify against
  the database collection, not the label.** Two admin surfaces can share
  almost identical labels ("External Contacts" tab vs. "External Contacts"
  page) while reading from entirely different MongoDB collections and
  backend routes. Before consolidating or removing what looks like a
  duplicate UI, trace both sides to their actual `dbUnified.read(...)` /
  `dbUnified.count(...)` collection name and route file — don't rely on
  matching page titles, tab labels, or even similar-looking table columns.

- **Generated HTML must never be hand-edited.** `admin-community.html`
  plus the 11 public `community-*.html` pages are all generated by
  `scripts/generate-community-pages.mjs` from one shared `shell(page)`
  template, gated by each page's `adminGuard` flag. Any fix belongs in the
  generator, not in the output file — hand-editing the HTML directly gets
  silently overwritten the next time someone runs the generator. After
  changing the generator, re-run it and diff every generated file to
  confirm only the intended page(s) changed.

- **An admin form that writes to a DB field is not proof the field is
  read anywhere.** `admin-content.html` had a whole "Homepage Hero
  Section" tab (title/subtitle/CTA, the _default_ tab) that saved to
  `content.homepage` — a field nothing on the live site ever reads;
  `index.html`'s hero heading is hardcoded static markup. Before trusting
  that an admin editing tool does something, grep for every reader of the
  field it writes (not just the obvious page — check whether the public
  page in question is even templated/dynamic, or fully static HTML like
  `index.html` and `faq.html` are here). A tool that silently does nothing
  is worse than no tool: it wastes an admin's time and they won't know why
  their change "didn't work."

- **Community's client-side modules must call `EFC.hideFallback()`.**
  `admin-community.html` (and the public community pages) render a real,
  server-side "noscript" fallback into `#efc-noscript` for no-JS/SEO,
  which every page-specific module is expected to hide once its own view
  has content — `community/home.js`, `discussions.js`, `member.js`,
  `thread.js` and `composer.js` all call `EFC.hideFallback()`, but
  `community/admin.js` didn't, so the fallback's own heading stayed
  visible forever, faintly overlapping the real UI. If you add a new
  community module, check it calls this too.

- **A `.form-control`-style class with `width: 100%` will stretch to
  fill a flex row unless something constrains it.** `admin-users.html`'s
  page-size `<select>` used a `form-control-sm` class that was referenced
  in the HTML but never defined in any CSS file, so it fell back to plain
  `.form-control`'s `width: 100%` and, as an unconstrained flex child,
  ballooned across the whole pagination row. When you see a `-sm`/`-lg`/
  variant class name in markup, grep for its actual definition before
  assuming it does anything — a missing modifier class fails silently,
  it doesn't error.

## Process lessons from this repo's admin audit

- **Don't run `prettier --write` on a whole `admin-*.html` file to "fix" a
  `prettier --check` warning.** Several of these files have pre-existing,
  unrelated formatting drift (hex case, attribute quoting, `<!DOCTYPE`
  case) that predates any of this work. Running `--write` on the whole
  file reformats hundreds of unrelated lines, burying your actual change
  in a huge diff. Before reformatting, diff the `--write` output against
  the original to confirm your own added lines are the only real change —
  if the file is drifted throughout, leave the drift alone and validate
  only your own added/changed lines match the surrounding style by eye.

- **`git checkout -- <file>` discards _everything_ uncommitted in that
  file, not just your last command's side effect.** If you use it to
  undo an accidental broad reformat (e.g. from the prettier mistake
  above), you will also discard any legitimate uncommitted edit sitting
  in the same file. Always run `git diff --stat <file>` first and confirm
  what you're about to lose before checking out; prefer manually reverting
  the specific bad change (or re-applying the good one from Edit history)
  over a blind checkout.

- **Delete dead code outright — don't rename-and-stub it.** When a
  function/section becomes genuinely unused (e.g. after replacing an
  embedded UI with a link to a canonical page), remove it completely in
  one edit. Renaming it to `_unused`/`_removed`/`_placeholder` with an
  `eslint-disable` comment as an intermediate step just leaves worse dead
  code behind if you stop there — go straight to deletion, then verify
  with a repo-wide grep that nothing else references the removed
  DOM ids/classes/function names.

- **This sandbox's network is flakier than a real browser's.**
  `net::ERR_TOO_MANY_RETRIES` and one-off "unstyled page" or
  "`X is not defined`" renders are common here and are usually the
  sandbox's proxy dropping a request, not a real bug. Before treating a
  screenshot as evidence of a bug, reproduce it more than once and/or
  cross-check against source code, a direct API/curl call, or in-page
  diagnostics (`document.styleSheets`, `getComputedStyle`,
  `typeof window.X`). Playwright needs
  `args: ['--disable-quic', '--disable-features=Quic']` and
  `ignoreHTTPSErrors: true` to behave reasonably here.

- **`github-advanced-security`'s Copilot-based check has a known,
  unrelated infra bug** (`CAPIError: 400 The requested model is not
supported`) that has recurred identically across multiple unrelated
  commits/PRs. If you see this exact error, it's not this repo's or this
  PR's problem — flag it once per PR, don't keep re-diagnosing it.

## Where things live

- Admin pages: `public/admin-*.html`, one file per page, sharing
  `admin-navbar.js`/`admin-navbar.css` (rendered into
  `#adminNavbarMount`) and `admin-shared.js` (`AdminShared.api()` /
  `adminFetch()` / `fetchWithTimeout()` — always fetch through these, not
  a bare `fetch()`, so network failures get a readable error everywhere).
- Per-page init scripts: `public/assets/js/pages/admin-*-init.js`.
- Admin API routes: mostly `routes/admin.js` (a very large file — search
  for the specific path rather than reading it linearly), plus dedicated
  files like `routes/admin-external-contacts.js` for some features.
- `dashboard-guard.js` gates every admin page client-side; it retries
  transient/ambiguous auth-check failures before redirecting to `/auth`.
