# PostHog Web Analytics recovery

## Findings

The Web Analytics error shown in PostHog is not generated by EventFlow's normal event payloads. PostHog's browser SDK owns `$process_person_profile` and emits it as a boolean. The failing query is trying to compare that boolean field with the UUID `019f6251-06a8-76c3-abe6-59e81e75cf04` while **Filter test accounts** is enabled. This points to a malformed PostHog project-level test-account filter, or historical malformed data, rather than the EventFlow page-view implementation.

The Installation Health recommendations are separate:

- **Web Vitals** was genuinely disabled in the EventFlow PostHog initialisation (`capture_performance: false`).
- **Reverse proxy** remains an optional infrastructure hardening measure. Direct EU ingestion is valid, and adding a proxy should be treated as a separate Railway/Cloudflare change with monitoring and rollback.

## Code changes

- Enable PostHog's standard `$web_vitals` capture after analytics consent.
- Keep Web Vitals attribution disabled to minimise payload size and data collection.
- Force `$process_person_profile` to boolean `false`, consistent with `person_profiles: 'never'`.
- Strip query strings and fragments from nested Web Vitals URLs before PostHog receives them.
- Bump the public analytics asset cache key so browsers receive the corrected integration.

## Required PostHog project cleanup

This repository change cannot edit PostHog project settings or rewrite historical events. In PostHog:

1. Turn **Filter test accounts** off temporarily and retry Web Analytics. If the dashboard loads, the project filter is confirmed as the immediate cause.
2. Open **Settings → Project → Internal and test users** (wording may vary).
3. Remove any rule using `$process_person_profile` with the UUID above, or any non-boolean value.
4. Recreate the filter using a genuine identifying property such as an internal email domain, a dedicated `is_internal` person property, or an internal hostname.
5. Turn **Filter test accounts** back on and retry the dashboard.

If the error remains with test-account filtering disabled, inspect historical events where `$process_person_profile` is not `true` or `false` and contact PostHog support with the failing query ID.

## Post-deploy checks

1. Accept analytics cookies on a non-sensitive public page.
2. Confirm a `$web_vitals` event appears with LCP, CLS, FCP or INP properties.
3. Confirm nested `$current_url` values contain no query string or fragment.
4. Confirm `$process_person_profile` is boolean `false`.
5. Refresh Installation Health after sufficient live traffic.
6. Verify sensitive routes such as `/auth`, `/verify`, `/checkout` and messaging pages remain excluded.
